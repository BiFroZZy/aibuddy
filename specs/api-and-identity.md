# Спецификация backend API и идентификации

## Идентификация

Для демонстрации реализуется mock SSO. Токен доступа содержит `user_id`, `role` и `team_id`; backend получает идентичность из проверенного токена и не доверяет роли или команде, присланным клиентом. В MVP не подключаются реальные HR- или identity-системы.

Роли и разрешения задаются явно и проверяются как в обработчиках endpoint, так и при вызове инструментов. Для неавторизованных запросов возвращаются разные статусы: 401 — пользователь не аутентифицирован, 403 — у него нет прав. Для отсутствующих ресурсов используется 404, если это уместно; тела запросов валидируются.

## Поведение API

Предусмотреть endpoints проверки работоспособности и готовности сервиса. React-клиент использует аутентифицированные HTTP endpoints для входа, получения текущего пользователя и контекста команды, адаптации, чат-сессий и сообщений, а также подтверждения и получения статуса действий. Для списков, которые могут расти, определить пагинацию. Ошибки возвращать в едином документированном JSON-формате.

Ответ чата содержит текст, метаданные и цитаты источников, а также статус инструмента/действия, если он использовался. Нельзя возвращать документы, к которым у пользователя нет доступа.

## Надёжность и наблюдаемость

Добавлять request ID в логи и ответы. Ограничивать время обработки запросов и частоту вызовов. Повторять с backoff только безопасные или идемпотентные операции. Сохранять переходы состояния действия (`pending`, `running`, `succeeded`, `failed`) и не превращать ошибку адаптера в успех. Генерировать структурированные audit/analytics-события без секретов и лишних персональных данных.

## Критерии приёмки

- Отсутствующий или неверный токен даёт 401; действующий токен без нужных прав — 403.
- Идентичность и команда пользователя берутся из проверенных claims.
- Ошибки API имеют документированную схему и не раскрывают stack trace или секреты.
- Контрактные и smoke-тесты API запускаются в CI.

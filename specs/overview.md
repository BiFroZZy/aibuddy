# AI-buddy: продуктовая и архитектурная спецификация backend

## Назначение

AI-buddy помогает стажёру адаптироваться в конкретной команде: отвечает на вопросы о команде и инструментах со ссылками на источники, показывает прогресс адаптации и выполняет безопасное действие через корпоративный сервис или его имитацию. Основной пользователь — стажёр. Помощник не заменяет наставника в содержательной работе.

## Объём MVP

Сценарии P0:

1. Вход через mock SSO; определение роли и команды пользователя; показ профиля команды, контакта наставника, задач адаптации, статусов, прогресса и следующего шага.
2. Ответы на вопросы о команде и инструментах с командным поиском по базе знаний и цитатами. Если разрешённые источники не подтверждают ответ, помощник явно сообщает об этом.
3. Создание заявки на отгул через mock Absence Service: подтверждение пользователя, сохранение ID и статуса, событие аудита, защита от дублей.

Запрос доступа через mock Access Service — вторичный сценарий P1, после готового сквозного P0. MCP необязателен и включается feature flag; P0 должен работать через встроенные адаптеры.

## Архитектура

Используется модульный монолит на Go, PostgreSQL и pgvector. React-клиент обращается к HTTP API на Go. Backend отвечает за идентификацию и RBAC, контекст команды, адаптацию, чат, оркестрацию AI, поиск знаний, реестр инструментов, адаптеры интеграций, аудит, аналитику и feature flags. LLM и корпоративные сервисы доступны только через интерфейсы и адаптеры backend. У модели нет прямого доступа к БД и корпоративным API.

Redis необязателен. Планировщик не входит в P0. Используются только синтетические демонстрационные данные; демонстрационные инструкции явно помечаются как неофициальные.

## Требования к качеству

- Проверять роль и принадлежность к команде на API и на границе каждого инструмента.
- Фильтровать документы по ACL до retrieval; утечек между командами быть не должно.
- Обычные локальные операции должны отвечать быстро (цель — менее секунды); для медленных запросов к LLM показывать загрузку, таймауты и ошибки.
- Использовать идемпотентность для операций записи и никогда не сообщать об успехе при ошибке адаптера.
- Добавлять структурированные логи, контекст запроса/трассировки и аудит действий.
- Целевое покрытие прикладного backend-кода тестами — выше 80%; CI должен воспроизводимо формировать отчёт.
- Чистый клон должен запускаться через Docker Compose, миграции и seed-данные и проходить smoke E2E без внешних ключей (fake-режим LLM).

## Демоданные и достоверность

Все пользователи, команды, документы, правила и ответы сервисов синтетические. Нельзя выдавать демонстрационные процессы за реальные правила Авито или использовать реальные данные сотрудников. В README и презентации следует отделять факты кейса от проектных решений.

## Основание для наполнения знаний

Демо-база может использовать приложенный чек-лист стажёра и публичные материалы AvitoTech, перечисленные в `knowledge-sources.md`. Эти источники задают содержимое демонстрационного сценария; архитектура и требования к backend в этом документе остаются проектными решениями для хакатона.
